## Part B2: Critique (Part 2)

### Example 1: Getting blog posts through the API
- Original behavior: The blog page used readBlogs() to read the JSON file directly on the server. It displayed the posts, but it did not call GET /api/blogs as the assignment required.
- My decision: I asked Viber to make the page fetch posts through the API and keep the existing layout and links. I also asked for loading and error messages, with a retry button.
- Why: I wanted the page to meet the API requirement and make it clear when posts were loading or could not be loaded.
- Files: components/BlogsList.js, app/blogs/page.js, app/blogs/blogs.module.css.
- Check: Viber confirmed the GET /api/blogs request in the browser network log and checked that the existing post appeared and opened. It slowed a response to check the loading message, blocked a request to check the error message, and confirmed that retry worked. On temporary storage, it also created a post and checked that it appeared without restarting the server. All 11 tests and the production build passed at that stage.
- Result: The blog listing now uses the API and gives feedback while loading or after a failed request.

### Example 2: Keeping messages and posts from being overwritten
- Original behavior: Saves could overwrite each other when they happened at the same time. A reported test showed 10 saves reporting success, but only 1 entry remaining. The contact storage helper also treated damaged JSON as an empty list, which could cause earlier data to be overwritten.
- My decision: I reviewed that finding and asked Viber to make saves take turns for each file. I also asked it to preserve damaged files and return an error. I did not run the original test myself.
- Why: A message or post should not disappear after the site says it was saved.
- Files: lib/fileLock.js, lib/blogs.js, lib/submissions.js, lib/storage.test.js.
- Check: Viber added five storage tests and tested 10 simultaneous requests to each API using temporary storage. All 10 contacts and all 10 posts remained, with unique IDs and blog slugs. It also checked that damaged files produced errors and stayed unchanged, and that both contact forms and the blog still worked. All 16 tests and the production build passed.
- Result: Saves no longer overwrote each other in the tested single-server setup. Damaged files were preserved, while missing files could still start as empty lists. The lock works within one Node server process; it was not tested across multiple servers.

### Example 3: Showing the right message during submission
- Original behavior: Starting another submission could leave the previous success message on screen. The blog form could also show an outdated or empty post link while the next request was still saving.
- My decision: I asked Viber to clear old feedback and post links when a submission starts, show “Sending...” or “Publishing...” while waiting, and show success only after the new request succeeds. If it fails, the entered text should stay in the form.
- Why: I wanted users to know what was happening with their current submission, without confusing it with the previous one or losing what they typed.
- Files: components/ContactApiForm.js, components/BlogComposer.js, components/ContactForm.module.css.
- Check: Viber tested a successful submission followed by delayed and failed submissions using temporary storage. It confirmed that old feedback disappeared, the button stayed disabled while waiting, and a failure kept the entered text. A successful second blog submission showed the new post's link. All 16 tests and the production build passed.
- Result: The forms now show the current request's status, clear old success feedback while saving, and keep entered text when a request fails.
